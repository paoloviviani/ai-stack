# The relay / daemon connectivity PoC for ADR 0085 — one box, three containers.

Topology (nothing else is reachable; the control path *must* cross the relay):

    [driver "chat server"]  ── cloud ──>  [relay]  <── natchost ── [userbox "user's NAT'd machine"]

- `userbox` runs the paseo daemon from the official image with the daemon
  bound to **127.0.0.1 inside the container** (`PASEO_LISTEN=127.0.0.1:6767`)
  and no published ports — the loopback bind is the NAT: no other container
  can reach the daemon port even in principle. The only egress it has is the
  daemon's own outbound dial to the relay.
- `relay` is paseo-relay built from the pinned source SHA below.
- `driver` is the Cerea-proxy stand-in: a Node process using
  `@getpaseo/client@0.8.0`, connected to the relay as an E2EE client with the
  daemon public key from the pairing offer — exactly the identity/credential
  model ADR 0085 records. It is on the `cloud` network only; it cannot
  resolve or reach `userbox`.

## Run it

```sh
docker build -t paseo-relay:3fc41c9 /tmp/opencode/paseo-relay-src   # the pinned source checkout
docker compose up --build -d relay userbox                          # relay + NAT'd daemon
./scripts/wait-for-offer.sh                                         # daemon up -> offer.json written
docker compose up --build driver                                    # runs the scripted sequence
```

The pairing handoff is `offer/offer.json`: the userbox entrypoint runs
`paseo daemon pair --json` against its running daemon and drops the offer
(the trust anchor — serverId + daemon public key + relay endpoint) on a
shared volume, standing in for "the user scans the QR into the chat".
The driver reads only that file.

## What the run demonstrated

Recorded verbatim in `transcript/run.log` (committed next to this README):

1. **Pair** — offer generated by the NAT'd daemon, consumed by the driver
   over the shared volume; the driver connects to `ws://relay:4000/ws?…`
   with `role=client`, `v=2` and the daemon's Curve25519 public key, and the
   daemon accepts commands only after the encrypted handshake completes.
2. **List / create an agent** — `fetchWorkspaces`, `fetchAgents`, then
   `createAgent` (provider `opencode`, model `cortecs/glm-5.3-flash`,
   `providerOptions.permission = {edit: "ask", bash: "ask"}`, mode
   `build`) with an initial prompt that writes a file.
3. **Stream the timeline** — `subscribeAgentTimeline` through the relay,
   user/tool/assistant frames arriving live.
4. **Approve a permission** — the agent's file edit surfaces a
   `permission_requested` event through the relay; the driver answers with
   `respondToPermission(behavior: "allow")` and the agent proceeds.
5. **Read a diff** — `getCheckoutDiff(cwd, {mode: "uncommitted"})` returns
   the parsed diff of the file the agent wrote.
6. **Q1, multi-client** — a second, independent encrypted client connects
   to the same daemon through the relay while the first is still subscribed,
   lists the agents, and observes the same timeline state. One relay, one
   daemon, two independent pairings-since-handshake client sessions.
7. **Negative control** — the driver cannot reach the daemon's port at all
   (`userbox` unreachable from `cloud`), proving the relay is the only path.

## What this did not exercise

- The LLM leg is the box's existing opencode provider credential, not
  Pystino `/v1` — no live gateway exists here; that axis is the enrollment
  workstream's live verification (ADR 0084/0040), deliberately untouched by
  this PoC.
- The daemon's web UI and its direct (non-relay) client paths were not
  used; everything the driver did went through the relay.
