# 0096 — Chat-only people: per-capability group flags

- Date: 2026-10-13
- Status: **accepted** 2026-10-14 (`Pystino@4e01a75`, `Cerea@d06cb0e5`).
- Amended: 2026-10-14 — capabilities are per-group flags and the setting defaults new groups (the amendment below supersedes in place).
- Amends: 0095 (the access-group gate answered who may use the deployment at all; this answers which *capabilities* a person who may use it holds), 0074 (the `/v1/me` contract gains `capabilities`).
- Related: 0089 (the machine agent and its enrollment), 0075 (what a coding agent may do once allowed is a separate permission framework).

## Context

A deployment may want some people to use the chat and nothing else — no coding agents, no API keys — while others keep everything. Two capabilities cover it today: **`code_agents`** (the `/code` panel and the machine links that serve it) and **`api_keys`** (minting and using `gwk_` keys). Restricting them per person needs a place to decide it (the console), a base value (the environment), and a per-group flag to grant it — and the decision must survive the shape this codebase already has: memberships are the only per-user fact the `/v1` path loads, and the join gate (ADR 0095) established that a refusal a group could restore must be a 403, never a 401.

## Decision

1. **Two capabilities: `code_agents` and `api_keys`.** Each has a deployment setting — `everyone` (the default, so an upgrade changes nothing) or `groups` — stored next to the join mode in the console's identity policy, with an environment baseline (`GATEWAY_ACCESS__CODE_AGENTS`, `GATEWAY_ACCESS__API_KEYS`). The setting reuses the `oidc_config` row-over-env fold and the carry-forward-on-write of the OIDC policy (ADR 0048, ADR 0095); no second mechanism is built.
2. **A group flag per capability** (two booleans on `groups`, migration 0059, default false). Console → Groups shows them as two toggles per group.
3. **Effective capability** is a pure function of the person and the folded policy: `everyone`, OR `is_admin`, OR an active membership (any source) in an active group carrying the flag. It is computed from memberships the auth path already loads — the `/v1` path runs no extra query and `test_query_counts.py` stays green. Admins are exempt so a misconfiguration cannot lock administrators out of the surfaces that fix it, the same reasoning as ADR 0095.
4. **`GET /v1/me` gains `capabilities`** (`{"code_agents": bool, "api_keys": bool}`). An older gateway without the field means *allowed*: Cerea treats absence as permission rather than as a refusal, so the upgrade order never breaks the chat.
5. **`code_agents` is enforced on the machine link.** A bearer token whose client is the machine client (matched on `azp`/`client_id` exactly as the accepted-clients check does; the default name is `opencode-enrollment`) from a user without the capability is refused **403 `agents_not_allowed`** on every `/v1` route, `/v1/me` included, so Cerea can read the refusal and its reason in one response. The path stays write-free (no audit write). Chat-client tokens are unaffected.
6. **`api_keys` is enforced at mint and at use.** `POST /api/me/keys` (and any admin route that mints for a user) refuses 403 `api_keys_not_allowed` without the capability; using an existing key whose owner lacks it is refused with the same code at key resolution, next to the ADR 0095 group-gate check. Keys are **not** deleted, so regaining the capability restores them. `opencode-install.sh` explains the refusal plainly when it sees the code.
7. **Cerea gates the panel on the capability.** `CODE_AGENTS_ENABLED` stays the outer switch (off = off for everyone). When it is on, a Pystino gateway's person's `/v1/me` `capabilities.code_agents` decides, cached with the session's existing `/v1/me` data; a non-gateway deployment is decided by the env switch alone, as today. The machine link treats 403 `agents_not_allowed` exactly like `outside_access_groups`: close with **4404**, do not revoke the device.

## Consequence

`galopin` already retries on a 4404 close and on a handshake 403, so no change to the agent is needed. Keys are deliberately left in place on a lost capability, matching the ADR 0095 posture that a loss a group can restore must not force re-enrolment or re-minting.

## Rejected

- A third "chat-only" boolean on the user: capabilities are derived from memberships, never stored, so a group change takes effect at the next decision instead of being another per-user flag to keep in step with groups.
- Enforcing `code_agents` per-route in Cerea only: the gateway is where the machine-link credential is authenticated, and a gateway-side 403 keeps a chat-only person's machine from ever establishing a session the client then has to close.
- Refusing a missing `capabilities` field as denied: an older gateway is not a refusal, and failing closed would break chat/code for every deployment until both halves upgraded in lockstep.

## Amendment 2026-10-14: capabilities are per-group flags

Deploying the decision above surfaced a coherence problem: with the mode defaulting to `everyone`, the per-group flag granted nothing anyone did not already hold, and with `groups` the mode was a second, silent grant path that made "the flag decides" untrue. The redesign removes the mode. The original body stands as the record of what was decided on 2026-10-13; this amendment supersedes it in place where the two disagree (decision 1's mode, and the startup consequence of item 5).

1. **The flag-only model.** A capability is only a per-group flag: a person holds `code_agents` or `api_keys` when they are an administrator, or hold an active membership (any source) in an active group with the flag on. There is no "everyone | groups" mode that gates access any more. A person in no group holds neither capability — the edge case the model allows; in practice the default group (`GATEWAY_OIDC__DEFAULT_GROUP`, `users`) is granted once at first sign-in, so everyone arrives holding what it carries, and only an administrator's removal of that membership (or of the group) can leave someone with neither.
2. **The deployment setting is the default flag new groups are created with.** `GATEWAY_ACCESS__CODE_AGENTS` / `GATEWAY_ACCESS__API_KEYS` keep their names; the value is now `on` (the default) or `off`, and the old `everyone` / `groups` spellings still parse for one release with a deprecation warning (`everyone` means `on`, `groups` means `off`). Every group created from now on gets its flags from this default — console **New group**, the Map dialog's *new group*, `group_import=auto`, and the groups SCIM or a directory pull creates. Console → Settings shows and saves the default with the same row-over-env fold as before (a decision there wins).
3. **Migration 0060** reads each capability's folded mode exactly as 0059 left it — the newest `oidc_config` row's column, else the environment, else `everyone`: `everyone` sets the flag **on** for every existing group, because that is what was in force, and leaves the new-group default `on`; `groups` leaves the stored flags untouched and the new-group default becomes `off`. The resulting defaults are recorded in one appended carry-forward row (reason `migration 0060: capabilities became per-group`), so the policy poll keeps reading them and a newly created group defaults the way the upgrade left things. No schema change: 0059's columns stand.
4. **Bulk actions on Settings**, one pair per capability: **Turn on for all groups** and **Turn off for all groups**. Each first shows a confirm with the preview — how many active, non-admin people gain or lose the capability — then applies to every group in one transaction, audited once as `group.capability_bulk` with detail `{capability, value, count}`. The per-group checkboxes on Groups are always live and show the stored flag; a flip takes effect at the next decision, since the bearer path re-reads memberships on every request.
5. **The machine-client refusal moves from startup to where the state is.** A PATCH that switches a group's `code_agents` off, and the bulk turn-off alike, are refused **400** while the machine client (`GATEWAY_OIDC__MACHINE_CLIENT_ID`, default `opencode-enrollment`) names a client that is not in a non-empty `GATEWAY_OIDC__ACCEPTED_CLIENTS`, with the error naming the setting to fix: a machine token is refused before the gate runs, so the restriction's machine-link half could never fire. Granting is always fine, and `api_keys` never trips this. For flags that predate that refusal — or an environment changed under them — the policy resolver logs an **ERROR** once per distinct state while any active group has `code_agents` off and the machine client is not accepted. The 0.7.x startup refusal for an env-baseline mismatch is removed (there is no mode left to read); the advisory startup warning for a likely misnamed machine client stands.
6. **Unchanged:** enforcement and the Cerea contract — 403 `agents_not_allowed` on every `/v1` route for machine-client tokens (`/v1/me`'s body still carries `capabilities` so the client can tell why), 403 `api_keys_not_allowed` at mint and at key resolution, keys refused not deleted, and the machine link closed with 4404 without revoking the device.

**Rejected in this amendment:** keeping an "everyone" mode that bypasses groups — it made the flag meaningless (with `everyone` in force the flag granted nothing anyone did not already hold) and the upgrade story incoherent, since the migration could not tell a decision from a default; and refusing at startup on an env baseline mismatch — there is no mode left to read, and the resolver's once-per-change ERROR covers the console-set case the refusal was aimed at.
