# Review: user management and identity providers plan (2026-09-25)

Reviewed against Pystino `origin/main` at `ba25a9a`, Cerea `origin/main` at `e4b06bfd`, cerea-deploy at `e8a178d`. Read-only; nothing was run or changed. Paths below are relative to each repo: `gw/` is `apps/gateway/src/gateway/`, `console/` is `apps/console/src/routes/`.

## Verdict

The plan diagnoses the right problem (a console-side IdP switch splits the two apps and can strand every admin), and its standing guards and staged switch are sound in outline. But three of its factual premises are wrong in ways that change the design: (1) `link_local_by_email` cannot link an Authelia identity to a Keycloak identity at all, it adopts only `issuer="local"` password accounts that no longer exist, so the plan's identity-linking step has no existing mechanism behind it on the gateway side; (2) `./configure --idp` already exists, but on any deployment that has started once it changes the chat and *not* the console, because the seeded provider row is authoritative and startup only back-fills empty fields, so the "alternative" is not a working alternative today either; (3) Cerea keys users on `(issuer, sub)` and refuses cross-issuer logins, so an IdP switch orphans every chat conversation unless `CHAT_MIGRATE_ISSUER_FROM` is set, which the plan never mentions. Proposal A is the wrong first investment for a homelab/team product: it puts the IdP connection on a runtime code path in both apps for a switch an operator does once. The safe first milestone is much smaller than the plan's phase 2: promote the Authelia People dialog to the Users page, add a self-service password change with its own throttle, and write down the break-glass. Everything about switching IdPs should go through `./configure` plus a startup re-seed, with the runtime candidate/test-sign-in flow deferred.

## Factual corrections

1. **"Signing in through a different IdP creates a new user … unless `link_local_by_email` is on."** Wrong. Linking matches `(issuer="local", subject=<casefolded email>)` only: `gw/oidc.py:489` (`_LOCAL_ISSUER = "local"`) and `gw/oidc.py:566-567`. The local password door was removed (`gw/config.py:186-199`, ADR 0088 D3), so on a current deployment there is nothing to adopt. Two OIDC issuers are never linked by this switch. The plan's step B3 ("linked to the admin's existing user: a verified-email match") describes a feature that does not exist and must be designed, not reused.

2. **"`PYSTINO_BOOTSTRAP_ADMIN_EMAIL` promotes a user only while the deployment has no admin at all."** Slightly wrong, and the difference matters: the check is "no *active* admin" (`gw/oidc.py:850-854`). Deactivating every admin re-arms the bootstrap. This is both a hidden recovery path and a hidden takeover path (see Risks). Also, the env name on the gateway side is `GATEWAY_BOOTSTRAP_ADMIN_EMAIL`; `PYSTINO_BOOTSTRAP_ADMIN_EMAIL` is the cerea-deploy `.env` key that compose maps to it (`compose.yaml:213`).

3. **"Alternative: `./configure --idp …` the only switch. That's simpler."** `./configure --idp external` exists (`configure:55`, `configure:783-812`) and rewrites `OIDC_ISSUER`, `OIDC_KIND`, and the client vars. But the gateway only seeds from the environment when the provider table is empty (`gw/identity_registry.py:263-266`); on a running deployment startup merely back-fills an empty `internal_base_url` and a `generic` kind on rows whose issuer *already equals* the env issuer (`gw/identity_registry.py:298-378`). A changed `OIDC_ISSUER` never reaches the row. So today `./configure --idp external` moves the chat to the new issuer while the console stays on Authelia: the same split the plan attributes only to the console-side switch, in the other direction. The alternative needs a small gateway change (an explicit "re-seed from env" or "env wins" mode) before it works.

4. **"The console can add and enable IdPs at runtime, but those only affect the console's own sign-in page."** Correct: `gw/routers/auth.py:141-146` and `:481-497` list every enabled row, and with more than one the login needs `?provider=`. Note there is no active/primary provider concept anywhere in the gateway; "the active IdP" in Proposal A is a new notion.

5. **"The gateway refuses to disable or delete the last provider through which an admin can sign in."** Listed under standing guards as if it were partly there. It is not: `update_identity_provider` sets `is_enabled` with no check (`gw/routers/admin.py:2857-2858`) and `delete_identity_provider` deletes unconditionally, by design (`gw/routers/admin.py:2885-2897`, the docstring says deleting the last row is what the operator asked for). Both are new work.

6. **"the directory 'preassigned' entries already exist"** (C, external IdP pre-registration by email). Half true. `preassigned_groups` lives on `DirectoryEntry` rows (`gw/routers/directory.py:224-243`), which exist only after a pull adapter or SCIM has mirrored the directory (`gw/directory/engine.py:199-230`). Binding at login is by `preferred_username`, with the entry's email as a second check when present (`gw/directory/engine.py:361-381`), and runs only when `sync_adapter != "none"` (`gw/routers/auth.py:380`). For an external IdP with no sync there is no entry to preassign and no bind. "Pre-register by email" is a new feature, and email-keyed rather than username-keyed.

7. **Users page condition.** The People button requires `provider.kind === "authelia" && provider.source === "console"` (`console/AdminSettings.tsx:327`). Since `seed_from_env` writes a row on first start, `source` is `"console"` for every deployment that has booted, so the button appears for any Authelia-kind row. Fine, but worth knowing the condition is not "bundled" but "row of kind authelia".

8. **"With SMTP configured (`email_config`): turn on Authelia's own reset-password flow."** The gateway's SMTP settings (`gw/config.py:186-190`, `PasswordResetSettings`) belong to the removed local door and are a tripwire. Authelia's reset flow needs Authelia's own `notifier.smtp` block, and cerea-deploy sets the filesystem notifier (`authelia/configuration.yml:69-71`) with `password_reset.disable: true` (`:31-32`). Turning it on is a cerea-deploy config change plus a `--force-recreate`, not a gateway setting.

9. **The chat already exposes the enrollment issuer.** `codeOidcIssuerUrl: OIDConfig.PROVIDER_URL` is served from Cerea's feature-flags endpoint (`src/routes/api/v2/feature-flags/+server.ts:47`, typed at `src/lib/server/api/types.ts:102-108`). The one-liner's source exists on the chat side today, from `.env`.

10. **The chat has an IdP migration mechanism the plan does not mention.** `CHAT_MIGRATE_ISSUER_FROM` moves an account to a new `(issuer, sub)` on a login with a *verified* matching email (`src/lib/server/loginIdentity.ts:13-16, 52-62`); without it a `sub` seen under a different issuer is refused (`:38-44`). Any IdP switch must set this variable or every user loses their conversations. cerea-deploy neither sets it nor documents it.

11. **Authelia file ownership is already handled.** Authelia runs as PUID/PGID 1001, the gateway's uid (`compose.yaml:253-258`), and bootstrap chowns the volume (`gw/deploy/bootstrap.py:209-224`). The console's `0600` temp file (`gw/directory/authelia_users.py:73`) is therefore readable by Authelia. No fix needed; recording it because the plan's D relies on it.

12. **Minor:** `oidc_policy.py`'s module docstring still says the connection "is read once at startup and is not hot-reloadable" (`gw/oidc_policy.py:5-9`); the registry rebuilds a client on `updated_at` change (`gw/identity_registry.py:241-256`). Stale comment, but it is the kind of thing the ADR for A/B will trip on.

## Risks, ranked

**R1 (high): admin self-lockout is still possible, and the bootstrap re-arms silently.**
- Disabling a provider row has no guard (`gw/routers/admin.py:2857`); deleting the last row removes OIDC sign-in entirely (`:2885-2897`). An admin with one Authelia row and a half-configured Keycloak row can disable Authelia and be locked out before Keycloak has ever issued them admin.
- `update_user` lets an admin set `is_active=false` on any account including their own (`gw/routers/admin.py:2433-2450`, no self or last-admin check; only `delete_user` has a self check at `:2473-2477`). Deactivating the last active admin re-arms `promote_bootstrap_admin` (`gw/oidc.py:850-854`): whoever next signs in with a verified email equal to the bootstrap address becomes admin. On an external IdP, that address is whatever the IdP says it is.
- Recovery is `pystino admin grant`, which requires the target to have signed in once already (`gw/deploy/admin.py:27-30`) and to be unambiguous by email across issuers (`:31-35`). On a split deployment the same address exists under two issuers and the operator must know to pass `--issuer`.

**R2 (high): identity linking across issuers is unbuilt, and the obvious design (email match) is a takeover vector.**
- The gateway has no cross-issuer link. Building one keyed on email means an external IdP admin, or anyone who can set their own email at that IdP, can claim any Authelia account. Requiring `email_verified === true` narrows this to "the IdP vouches", which is the same trust the bootstrap already extends, but only if the console verifies the literal boolean (as `_adopt_local_account` does at `gw/oidc.py:554`), never a truthy string.
- Normalisation: gateway matches with `.strip().casefold()` (`gw/oidc.py:566`, `gw/deploy/admin.py:27`); Cerea's migration matches `email` exactly (`src/lib/server/loginIdentity.ts:53-56`, no casefold). Same person, two answers. Neither side does Unicode NFKC or punycode; a homoglyph address at a permissive IdP would pass casefold. For the bundled Authelia the console validates only `"@" in email` (`gw/directory/authelia_users.py:118`).
- The plan's B3 "confirmed explicitly" is the right instinct: a link should be a *console action by the signed-in admin*, binding their current session's user to the candidate identity they just proved. That needs no email at all: the gateway sees both subjects in one browser session. Email should be a hint shown in the confirmation, not the key.

**R3 (high): a partial switch is the default outcome, on both current paths.**
- Console path: changes the row, chat still reads `.env` (`compose.yaml:339`). `./configure` path: changes `.env`, the row stays (correction 3). There is no transaction spanning `.env`, the provider row and Authelia's client list, and Proposal A only closes the first gap.
- Even when both apps point at the new issuer, Cerea refuses old accounts unless `CHAT_MIGRATE_ISSUER_FROM` is set (correction 10), and the gateway creates new users with no memberships and no admin. galopin machines enrolled against Authelia hold refresh tokens the new issuer will not honour, and `CODE_MACHINE_ISSUER` defaults to the chat's issuer (`src/lib/server/code/machineAuth.ts:33`), so every enrolled machine drops off at the switch.
- Rollback: the Authelia row keeps its client secrets and the `authelia` profile can stay up, so rolling back the gateway is "re-enable the row". Rolling back the chat is a `.env` edit and restart. Rolling back Cerea's migrated accounts is not possible (`migratedFromSub` is recorded, but `hfUserId` has been overwritten). Rollback must be tested before the switch is offered.

**R4 (medium-high): the self-service password change bypasses Authelia's throttling and is a new oracle.**
- Authelia's regulation (bans after failed attempts; no `regulation:` block in `authelia/configuration.yml`, so its defaults apply) protects Authelia's login form only. A console endpoint that verifies the current password against the argon2 digest in the file is a second verifier with no throttle, no ban, and no shared counter. It needs its own per-subject and per-IP limiter and its own lockout, and ideally should *write* a ban Authelia sees. Authelia's SQLite regulation table is in `authelia-data`, which the gateway does not mount (`compose.yaml:216-217`), so sharing the counter means a second volume or accepting two independent limiters.
- Argon2 verify is slow by design (64 MiB, 3 iterations, `authelia/configuration.yml:36-45`): an unthrottled endpoint is also a memory-exhaustion lever against the gateway container.
- Subject binding: the gateway's user row carries `username` from `preferred_username` (`gw/oidc.py:889-891`), which is the Authelia login name and the users-file key. That is the right binding, but `username` is admin-editable (`gw/routers/admin.py:2453-2455`, `admin_edited_fields`). A console edit of `username` would let a password change land on someone else's entry. The endpoint must bind by the token's `preferred_username` at the time of the call, or by a subject-to-login map, not by `users.username`.
- Concurrent writes: `UsersFile` is load-modify-save with no lock (`gw/directory/authelia_users.py:60-83, 115-176`). Two admins, or an admin and a self-service change, lose one write silently. Authelia's watcher (`watch: true`, `:35`) reloads on each rename; the atomic replace is right, but whether Authelia's watcher survives inode replacement across many writes should be confirmed on the live stack, not assumed.
- Timing: the constant-time requirement applies to the argon2 verify (already constant-time in the library) and to "user exists" versus "wrong password" responses. Return the same error for both.

**R5 (medium): admin-shown one-time passwords.**
- Minted with `secrets.token_urlsafe(15)` (20 chars, `gw/directory/authelia_users.py:104`), shown once in a notice with no copy button (`console/IdentityDirectory.tsx:32-33`, the plan promises a copy button). Fine as a secret. The risks are delivery (admin pastes into chat/email) and lifetime (nothing forces a change on first login; Authelia's file backend has no "must change password" flag). Accept the delivery risk with a documented "use a one-time-secret channel" note, and treat "forced change on first login" as unavailable with Authelia file backend.
- Reset-password is a full password replacement by any admin with no audit row, which is also a takeover path for a malicious admin. Log it (R8).

**R6 (medium): pre-registration by email binding on first sign-in.**
- For bundled Authelia, the existing bind is by login name plus verified email (`gw/directory/engine.py:361-381`), and the console controls both sides of the file, so an invited identity cannot be claimed by an outsider.
- For an external IdP, an email-keyed invite is claimable by whoever the IdP says has that email. With `email_verified` required this is the IdP's word, which is the trust model already chosen. Without it, an invite carrying `is_admin` or a privileged group is a standing takeover. Recommend: invites carry roles and groups but never `is_admin`; admin is granted after first sign-in, by an admin, in the console.

**R7 (medium): disabling a user does not revoke everything.**
- Gateway sessions check `is_active` per request (`gw/deps.py:14, 67-68`): effective immediately. Cerea sessions ask `/v1/me` at most once a minute and fail open on network error (`src/lib/server/gatewaySession.ts:8-16, 61-64`): effective within a minute for a gateway-side deactivation. Authelia-side `disabled` (People dialog) is a *different* flag: it stops new Authelia logins but touches neither the gateway's `is_active` nor Cerea's session until the `authelia_file` sync runs (and only if it has been confirmed, `gw/routers/directory.py:163-181`). Two switches, two meanings, one word. The Users page must either write both or say which it wrote.
- Access tokens and galopin refresh tokens issued by Authelia are not revoked by either flag; they expire (access 1h, machine refresh 90d, `authelia/configuration.yml:75-79`). `/v1` bearer calls check `is_active` (`gw/deps.py:173, 408`), so the gateway refuses them; Authelia's own session is not touched.

**R8 (medium): no audit trail for identity actions.** Provider edits, user activation, admin grants, Authelia user creation, password resets and deletions log to stdout at best. `DirectorySyncRun` is the only persisted record in this area. For a team product, an append-only `identity_events` table with actor, target, action and reason is a small addition and should precede the password-change endpoint.

**R9 (low-medium): group-to-role mapping is per provider and `oidc_config` is global.** Group mappings live on the provider row (`gw/routers/admin.py:2840-2841`), but `auto_provision` and `unknown_user_policy` are one append-only global table (`gw/oidc_policy.py`). A candidate IdP and the live one share the same provisioning policy during a staged switch; "refuse strangers" on Authelia also refuses the admin's test sign-in on the candidate unless they are pre-registered. B2 must account for this.

**R10 (low): deleting a user who owns data.** Gateway side is thought through (`gw/routers/admin.py:2458-2510`: cascade keys and memberships, ledger set-null, refuse while they have published bases). Chat side is untouched: Cerea's Mongo user, conversations and files survive a gateway delete and an Authelia delete. `UsersFile.delete` refuses only the last user (`gw/directory/authelia_users.py:170-176`). The Users page should say what a delete does and does not remove.

**R11 (low): users file backup and restore.** Covered by the README's volume tar (`cerea-deploy/README.md:207-225`), but nothing tells an operator that the users file and the gateway's user table must be restored together, or that the gateway never recreates the file (`gw/deploy/bootstrap.py:189-199`, exists-check only).

**R12 (low): MFA/TOTP for bundled users is effectively unavailable.** `default_policy: one_factor` and clients at `one_factor` (`authelia/configuration.yml:47-48, 90, 108`); registering a TOTP device in Authelia's portal requires an identity-verification email, and the notifier writes to `/data/notification.txt` (`:69-71`), which no user can read. Either document "no MFA with the bundled IdP" or configure SMTP and switch clients to `two_factor` as an opt-in.

## Recommended changes to the plan

1. **Drop Proposal A. Make `./configure` the switch, and make it actually switch.** Add a gateway startup mode where the environment wins for the row named `default` when `OIDC_ISSUER` differs from the row's issuer (opt-in via an env flag `./configure` sets for one boot, or an explicit `pystino idp adopt-env` command run by `./configure`). Keep the old row, disabled, with a note. This closes correction 3 without runtime OIDC config in either app.

2. **Replace B's "candidate" with a configure-time rehearsal.** `./configure --idp external --rehearse` writes the new client to `.env`, and a `pystino idp check --issuer … --client …` command fetches discovery, and optionally runs one auth-code flow from the host with a device-code or a printed URL, reporting the claims it got (`email`, `email_verified`, `groups`, whether `admin_claim` matches). This gives B4's "the claim yields admin" check with no half-configured runtime state.

3. **Design the cross-issuer link as a session-bound console action, not an email match.** While signed in as an admin, "Link my account to the new IdP" starts an auth-code flow against the candidate and, on return, writes a `user_identities` row for the current user. The email is displayed for confirmation, and `email_verified` is shown, not required, because the binding is the browser session. For everyone else, migration is by verified email once, at first login on the new issuer, mirroring `CHAT_MIGRATE_ISSUER_FROM`, and gated by `email_verified === true`.

4. **Set `CHAT_MIGRATE_ISSUER_FROM` in the same `./configure` run** and document that the chat's migration is one-way.

5. **Add the guards as gateway rules, not console rules:** refuse `is_enabled=false` or delete on the only enabled provider that has at least one active admin identity; refuse `is_active=false` on the last active admin, including self; make `pystino admin grant` able to create the user row from `--issuer --subject --email` so recovery does not require a prior sign-in.

6. **Split "disable" on the Users page into what it means.** For Authelia users, a single "Disable" should write both the file flag and `is_active=false`, and say so. For external users, only `is_active`.

7. **Password change: gateway endpoint, own limiter, own audit, bind by token login name.** Rate-limit per username and per client IP, lock for a period after N failures, respond identically for unknown user and wrong password, write an audit row, and take an advisory `fcntl.flock` on the users file for every `UsersFile` write. Decide explicitly whether Authelia's own regulation is bypassed and say so in the docs.

8. **Add an `identity_events` audit table before any of C or D lands.**

9. **State the MFA position** for the bundled IdP in E.

10. **Documentation order:** break-glass and backup/restore first; they are prerequisites for letting anyone touch the switch.

## Answers to the open questions

**Runtime switch (A) or `./configure` only?** `./configure` only, with the gateway re-seed from recommendation 1. Reasons: an IdP switch happens once per deployment; A puts discovery and client secrets on a runtime path in two apps, requires Cerea to replace a module-level `OIDConfig` parse (`src/lib/server/auth.ts:44-64`) and a 10-minute issuer cache (`:293-316`) with per-request lookups, to invalidate the machine-auth JWKS cache, and to trust the gateway for its own login config, which inverts the current "gateway is authorisation authority, chat owns its login" split; and A still cannot rotate Authelia's client list or `.env`, so it does not remove `./configure` from the loop. The cost of A in Cerea is at least: a fetch-and-cache of OIDC settings from the gateway with a failure mode when the gateway is down at login, changes to `updateUser.ts` issuer resolution, and a new trust boundary. The cost of the alternative is one gateway CLI command and a docs page.

**Require `email_verified=true` for linking?** Yes, the literal boolean, for every *automatic* link and for the bootstrap, as `gw/oidc.py:554` and `:841` already do. Do not require it for the session-bound admin link (recommendation 3), because the binding there is the session, and some IdPs never send the claim. Also casefold and NFKC-normalise on both sides, and fix Cerea's exact-match migration query to casefold.

**Pre-registration: roles only, or groups too?** Groups and quotas, yes: they are what an invite is for. Roles in the sense of `is_admin`: no. Admin is granted after the person exists, by an admin, in the console, so an invite can never be a standing admin grant to whoever the IdP next assigns that address to.

**Where the enrollment one-liner's OIDC info comes from.** From Cerea's feature-flags endpoint as it stands (`src/routes/api/v2/feature-flags/+server.ts:47`), sourced from `.env`. With `./configure` as the only switch, `.env` *is* the active IdP, and the chat already validates machine tokens against that same issuer, so the one-liner and the validator cannot disagree. Add the public client id beside it. Unblock the one-liner now; it does not depend on any of A/B.

## Proposed minimal first milestone

Goal: a homelab or team deployment on the bundled Authelia where an admin adds people from the Users page and people change their own password, with no way to lock out the last admin. No IdP switching, no external-IdP UI changes.

1. **Guards (gateway).** Refuse deactivating the last active admin, including self; refuse disabling or deleting the only enabled provider. Extend `pystino admin grant` to create the row when given `--issuer` and `--subject`.
2. **Audit table.** `identity_events` written by provider CRUD, user activation, admin flag changes, Authelia create/reset/disable/delete, and the password change.
3. **Users page (console).** For an Authelia-kind provider: "Add user" and "Reset password" moved from the People dialog, one-time password shown once with a copy button, "Disable" writing both flags. Delete confirms what survives on the chat side. People dialog becomes a link.
4. **Self-service password change (gateway + console).** Bound to the token's `preferred_username`; per-user and per-IP limiter with lockout; identical errors; advisory file lock around every users-file write; audit row; no password in logs. Line-by-line review before merge.
5. **Docs.** Managing users with the bundled Authelia, backup and restore including the users file, break-glass, and the statement that MFA and SMTP reset are not available with the bundled IdP by default.
6. **Enrollment one-liner** from the feature-flags issuer plus client id.

Deferred: everything about switching IdPs (recommendations 1 to 4), external-IdP pre-registration by email, directory listings for unsynced external IdPs, and SMTP-backed Authelia reset. Cut: Proposal A.
